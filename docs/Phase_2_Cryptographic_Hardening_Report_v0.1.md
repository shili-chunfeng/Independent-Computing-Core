# 1. Scope

This hardening task repairs deficiencies in the existing Phase 2 — Cryptographic Foundation. It does not implement Root Identity, Device Enrollment, Identity Rotation, Recovery Protocol, or any other Phase 3 functionality, and it does not implement the future Phase 4 KeyStore.

The work addresses:

- Phase 0 C-009, C-010 and C-011;
- Phase 0.2 `INV-007`, Threat `T-PKG-007` and Security Gate S2;
- Phase 0.3 dependency-direction rules, §§44–50, 79–81, 88 and D-ARCH-004;
- Phase 2 cryptographic test, dependency, secret-material, and verification requirements;
- ADR-0001 layered dependency direction and fail-closed architecture boundaries;
- ADR-0002 Rust/Cargo 1.98.1 toolchain pinning;
- ADR-0003 the fixed ClassicalV1 cryptographic profile;
- ADR-0004 the portable crypto API/provider implementation boundary;
- ADR-0005 secret-material handling, zeroization, forbidden traits/serialization, and zeroization limitations;
- ADR-0006 reviewed profile migration, rejection of unauthenticated arbitrary algorithm negotiation, and rejection of silent downgrade.

The second review specifically closes fail-open gaps for inactive optional dependencies, renamed dependencies, dependency declaration features, exact direct-version requirements, repository packages outside the workspace, all-features resolution, and secret-wrapper trait evidence.

# 4. Dependency security policy

`deny.toml` and pinned `cargo-deny 0.20.2` enforce:

- advisory checks;
- yanked dependency rejection;
- license policy;
- registry/source policy;
- wildcard dependency rejection;
- duplicate-version rejection;
- banned dependency policy;
- banned `ed25519-dalek` `hazmat` and `legacy_compatibility` features.

`deny.toml` defaults its graph to all features, and CI explicitly supplies the all-features metadata file to cargo-deny. This prevents an ordinary local invocation or the formal CI invocation from silently restricting the audit to the default graph.

The architecture checker separately applies a complete declaration allowlist to every workspace package. It validates the true package name (not merely the manifest alias), alias, dependency kind, target condition, optional flag, source/path target, literal version requirement, `default-features`, and requested feature set. The seven reviewed external production declarations remain pinned exactly:

```text
zeroize          = =1.9.0
chacha20poly1305 = =0.11.0
ed25519-dalek    = =3.0.0
hkdf             = =0.13.0
sha2             = =0.11.0
x25519-dalek     = =3.0.0
getrandom        = =0.4.3
```

An inactive optional dependency, dev/build/target-only declaration, alias, broader semver requirement, extra feature, or re-enabled default feature therefore fails before its current lockfile resolution can make it appear harmless. The all-features resolved feature union is checked independently to detect feature unification through other edges.

The CI tool is installed as:

```bash
cargo install --locked --version 0.20.2 cargo-deny
```

It is D2 tooling, not a production ICC dependency. The advisories, bans, licenses, and sources checks over ICC's all-features metadata are required CI gates; their results are time-bounded evidence and are not an unsafe-code or maintenance-health audit. The separate Remaining Risk concerns the `cargo-deny` tool itself and its own transitive dependencies: a complete source-level and unsafe-code audit of that tooling graph is **NOT VERIFIED**. It does not mean that the required ICC dependency source-policy gate was omitted.

# 5. Standards-based cryptographic tests

No new primitive was invented.

## HKDF-SHA-256 — RFC 5869

Tests include:

- RFC 5869 Appendix A Test Case 1;
- the ICC API returns 32 bytes, so the test compares exactly the first 32 octets of the official 42-octet OKM;
- RFC 5869 Test Case 3 zero-length salt/info boundary case, again comparing the first 32 OKM octets;
- salt mutation changes output;
- IKM mutation changes output;
- info mutation changes output.

Reference: <https://www.rfc-editor.org/rfc/rfc5869>

## Ed25519 — RFC 8032

Tests include RFC 8032 §7.1 Test 1 and negative cases for exact public key/signature verification, tampered message, tampered signature, invalid public-key material, and invalid signature encoding/value.

`hazmat` and `legacy_compatibility` are not enabled and are blocked by repository policy.

Reference: <https://www.rfc-editor.org/rfc/rfc8032>

## X25519 — RFC 7748

Tests verify official known answers for Alice/Bob public keys and shared secret, plus all-zero/non-contributory peer rejection.

Reference: <https://www.rfc-editor.org/rfc/rfc7748>

## ChaCha20-Poly1305 — RFC 8439

Tests verify the RFC 8439 AEAD vector including exact ciphertext and tag, plus wrong key, wrong nonce, wrong AAD, tampered ciphertext, tampered tag, truncated authenticated input, and an empty-plaintext/empty-AAD boundary round trip.

Reference: <https://www.rfc-editor.org/rfc/rfc8439>

## Algorithm identifiers

`algorithm_ids_are_stable_for_v1` includes both `KdfAlgorithmId::HkdfSha256` and `KdfAlgorithmId::Argon2idV13`. Argon2id remains an identifier/reserved future password-KDF choice; no KeyStore/password lifecycle was implemented here.

# 6. Secret material and App boundary

The earlier CLI signing demo constructed an `Ed25519SigningSeed` from a raw `[u8; 32]` buffer. A first hardening step removed that raw signing operation, but the CLI still directly depended on `icc-crypto-api` and `icc-crypto-rust`. Because provider methods can return secret wrapper values through type inference, identifier-only source scanning was not a sufficient technical boundary.

The acceptance-gap fix therefore removes both direct dependencies from `apps/indie-cli/Cargo.toml` and removes `crypto-demo` entirely. `doctor` and `demo` remain the CLI commands.

The current production dependency policy rejects:

```text
App -> icc-crypto-api
App -> icc-crypto-rust
```

This is repository/CI dependency-topology enforcement. It is **not** a Rust visibility guarantee, runtime sandbox, or formal proof that arbitrary code could never be changed to expose a secret.

No new facade, service, Phase 3 Identity functionality, or Phase 4 KeyStore was created to preserve the demo.

Secret wrappers still zeroize their owned `[u8; 32]` storage on Drop, subject to the documented limitations around compiler-created copies, registers/stack, third-party temporaries, hostile root/kernel memory access, swap/hibernation/crash dumps, and physical/microarchitectural side channels.

# 7. Architecture enforcement

`scripts/check_architecture.py` consumes both default and all-features locked metadata and uses a fail-closed **per-package declaration** policy rather than treating every `crates/core/*` package as a single permissive class.

Every current workspace package has explicit allowed dependency declarations. The checker reads `packages[].dependencies`, so inactive optional declarations are covered, and separately validates `resolve.nodes[].deps` in both graphs. Every repository Cargo package other than the virtual workspace root must be a formal workspace member. Actual Cargo package identity is used, so a manifest alias does not bypass either declaration or resolved-graph policy.

The reviewed Phase 1 edge:

```text
icc-identity-core -> icc-platform-api
```

is encoded only for `icc-identity-core`; it does not widen all L2/Core dependencies.

Policy tests explicitly reject:

```text
L0 -> L2
L0 -> L3 Port
L1 -> L2
Domain Core -> crypto provider
Platform Port -> Linux adapter
App -> internal crypto API
App -> crypto provider
unknown workspace package
unreviewed external direct dependency
inactive optional dependency, including reqwest
unreviewed dev, build, or target-specific dependency
renamed dependency judged by its actual package identity
broadened direct-version requirement
default-feature or requested-feature drift
forbidden all-features feature union
repository package outside the workspace
```

The secret-type checker scans all Rust source under `icc-crypto-api/src`, not only the macro body. It conservatively rejects `Copy`, `Clone`, `Debug`, `Serialize`, and `Deserialize` through the current macro/direct-struct derive forms, intervening attributes, ordinary or qualified explicit impls, dependency and trait aliases, and type aliases. It also fails if an expected secret wrapper declaration disappears.

Negative fixtures cover those recognized forms and explicitly document that arbitrary macro-generated implementations cannot be reliably expanded by this dependency-free source-pattern checker.

Separately, `icc-crypto-api` contains fifteen independent `compile_fail` doctests: one block for every combination of five secret wrappers and the `Clone`, `Copy`, or `Debug` trait. Because every assertion is isolated, one still-forbidden trait cannot mask an accidental implementation of another. These are compiler-level regression checks for the current Rust types, but they are not formal verification. `Serialize` and `Deserialize` remain defended by the exact dependency-feature policy plus the full source-pattern scan; the secret API does not gain a serde dependency.

The checker also retains locked-graph, Core OS/API token, no_std, forbidden Ed25519-feature, secret-identifier-outside-boundary, and first-party production unsafe checks.

The source checker explicitly remains **conservative source-pattern/metadata analysis**. It is not a Rust parser or AST, does not expand arbitrary macros, and is not compiler verification, a visibility proof, a runtime security boundary, or formal proof. The isolated doctests are the distinct compiler-level layer for `Clone`, `Copy`, and `Debug` only.

# 10. Phase 2 v0.1 documentation erratum

The original `docs/Phase_2_Cryptographic_Foundation_v0.1.md` is retained as a historical baseline rather than silently rewritten.

Its §52 wording implied that a secret Clone/Debug scan had already been implemented/passed at initial Phase 2 delivery. The original delivery did not have sufficient CI evidence for that claim.

**Correction:** secret-wrapper boundary enforcement was added during Phase 2 hardening and later strengthened to scan all crypto-API Rust source for the recognizable forbidden-trait forms described above. Architecture fixtures test that source-pattern logic. Fifteen isolated compile-fail doctests provide the distinct compiler-level regression evidence for `Clone`, `Copy`, and `Debug`; no claim is made that the source scan is compiler, AST, visibility, runtime, or formal proof.

No historical checkbox should be interpreted as current completion evidence without the final CI/PR evidence.

# 11. ADR impact

- **ADR-0001 — Layered Dependency Direction:** defines inward layered dependency direction and the architecture boundaries that this hardening makes fail closed.
- **ADR-0002 — Pin Phase 1 to Rust 1.98.1:** defines the Rust/Cargo 1.98.1 toolchain pin used by the verification gates.
- **ADR-0003 — Classical Crypto Profile v1:** fixes ClassicalV1 as SHA-256, HKDF-SHA-256, Ed25519, X25519, and ChaCha20-Poly1305, with Argon2id reserved for its documented future low-entropy purpose.
- **ADR-0004 — Crypto Provider Boundary:** defines the portable `icc-crypto-api` interface and provider-implementation separation from crates such as `icc-crypto-rust` and its concrete dependencies.
- **ADR-0005 — Secret Material and Zeroization:** governs secret-material confinement, best-effort zeroization, prohibition of `Copy`, `Clone`, `Debug`, and serialization, and the limits of software zeroization.
- **ADR-0006 — Crypto Agility and Post-Quantum Migration:** requires migration between reviewed profiles and rejects unauthenticated arbitrary algorithm negotiation and silent downgrade.

This documentation correction changes none of those accepted decisions, and it changes neither the dependency set, algorithms, provider boundary, secret policy, nor threat model. No new ADR is required because it corrects traceability to existing decisions rather than introducing a new architectural decision.
